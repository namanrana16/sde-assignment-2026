# Thresholds: derivation and sensitivity

Every tunable in `controller/settings.py` that gates a detector or an allocation, with the reasoning that fixes
its value. The rule: a threshold is derived from (a) the guardrail magnitude the brief gives (a 2% drop on the
guarded KPI is "harmful"), (b) effect-size / power arithmetic, or (c) the workflow's own policy values read over
HTTP (`min_validation_pass_rate`, `objective.guardrail`, `max_shift`). None is fitted to a public scenario's
hidden truth. Where a value is a prior, it says so. `docs/CONTEXT.md` is left unchanged.

Notation: p0 = a typical pickup rate (~0.3); se_rel(n) = sqrt((1-p0)/(n p0)) is the relative standard error of a
pickup rate: n=100 -> 15%, n=150 -> 12%, n=1000 -> 4.7%.

## Caller-ID health (C5)

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `DID_H_FLOOR` | 0.25 | Prior for the worst plausible relative health of an untested number. Carrier spam labelling is commonly reported to cut answer rates by about 75%, so a labelled number answers ~1/4 as often. Previously 0.35. Lower = more conservative probe cap. | Probe cap at h_bar=0.9: floor 0.35 -> 2.5%, 0.25 -> 2.1%, 0.0 -> 1.5%. |
| `DID_PROBE_BASE_STEP` | 0.015 | Harmful line is -2% on the guarded KPI; 0.5pp reserved for measurement noise. The cap `s <= 0.015 h/(h-h_floor)` keeps the worst-case DID-health step below 1.5%. | Linear: 0.01 -> cap 1.4%; 0.02 -> 2.8% (touches the line). |
| `DID_PROBE_MAX_SHARE` | 0.25 | Clamp used when h_bar <= h_floor, where the formula diverges (fleet already as bad as the worst case, a probe cannot hurt), and a global bound on any probe. | Only active when the whole fleet is unhealthy. |
| `DID_REPROBE_HARM_BUDGET` | 0.005 | A re-probe of a number whose flag expired is a second look at a known-bad candidate: it may cost at most a quarter of the 2% line. Gives share = 0.5% x h/(h-floor), about 0.7%. | Budget 0.01 -> ~1.4%: faster verdict, but residual traffic on a once-flagged number is more likely to be read as harm. |
| `DID_FLAG_MIN_DROP` | 0.12 | Effect-size gate. A number holding share s whose pickup falls by d costs the workflow s*d. At the smallest useful split (2 DIDs, s=0.5) a 12% step costs 6% = 3x the 2% guardrail; smaller steps are not worth an incident. Previously 0.30, which hid a 15-20% step. | The p gate is the real limit; at 0.08 a mild fatigue wobble starts to qualify. |
| `DID_FLAG_P` | 1e-5 | CONTEXT C5 asks p<0.001 per test; the test is repeated every tick on 4 windows (~130 looks per DID-day), so Bonferroni-style 0.001/100. | Detecting a 15% step needs ~3300 dials per side at 1e-5 (z=4.26), ~2700 at 1e-4. At 1e-3 false flags appear every few days. |
| `DID_FLAG_P_UNFITTED` | 1e-7 | While the fatigue curve is flat/cold, load effects cannot be adjusted away, so a drop may be fatigue. Two orders stricter. | Cold-start workflows flag only on large clear steps. |
| `DID_FLAG_WINDOWS_HOURS` | 1,2,3,6 | CONTEXT uses 3 h; a 6 h window adds power for 15-20% steps while diluting a step by at most the pre-step hours. | Longer windows add power and dilute the estimated drop. |
| `DID_FLAG_PERSIST_EVALS` | 2 | The condition must hold on 2 consecutive evaluations: screens one-tick outliers. | 1 reverts to the old behaviour; 3 costs another 15-60 min of detection time. |
| `DID_FLAG_COOLDOWN_MINUTES` | 2 days | A flag is not permanent: labels decay. After 2 days and complete evacuation the number is re-probed at the re-probe cap. Order of the fatigue time constant (days). | Longer = fewer re-probes; production would use about a week. |
| `DID_SHARE_WINDOW_HOURS`, `DID_SHARE_MIN_DIALS` | 12 h, 50 | Observed share needs enough dials: 50 dials give a share standard error of at most 7pp. Widens to 24 h if short. | Larger window = slower to notice an evacuation completing. |
| `DID_EVAC_CLOSE_SHARE` | 0.005 | An evacuation closes when the flagged number's observed trailing share is below 0.5% (the re-probe harm budget). | Higher closes earlier but hides residual traffic. |
| `DID_WEAK_MARGIN` | 0.15 | Materiality: a DID whose pickup at comparable load is >=15% below peers costs, at a 3-way split, 5% = 2.5x the guardrail, so removing it is worth an approval slot. Previously 0.20. | At n=150 (se_rel 12%) a weak base is confirmed only when ~50% below; with the 48 h window (n~1000) ~30% below. |
| `DID_PASS_RATIO`, `DID_PASS_Z` | 0.775, 1.645 | A probed DID passes when its load-adjusted pickup ratio is >= 1 - 1.5 x margin (halfway between healthy and the materiality line, widened by the ~15% standard error at n=100) and it is not significantly (p<0.05) below the materiality line. A looser z-only rule let a 0.55-health number pass ~1 time in 6 at the minimum n; a point rule at the 0.85 line failed ~1 in 6 healthy ones. A DID that misses the bar stays 'suspect' (probe cap at most) and is re-judged each tick, so a healthy one is delayed, not stranded. | 0.85 fails more healthy DIDs at n=100; 0.7 admits ~9% of 0.55-health DIDs. |
| `DID_PASS_MIN_DIALS` | 150 | se_rel(150) = 12%. With the 0.775 bar a 0.62-relative-health number (a 0.55-health DID next to loaded peers) passes about 2% of the time, against 16% at n=100 (one false pass was graded harmful on public_01). Probing a 2% share takes ~2 days instead of ~1.4. | Doubling n shrinks the standard error by sqrt(2). |
| `DID_PASS_MIN_AGE_HOURS` | 24 | CONTEXT: "after >= 1 day passing". | - |
| `DID_FLAG_MIN_DIALS` | 150 | Each side of the step test (CONTEXT C5). | - |
| impact override (safety DID moves) | `min(1, moved share x relative pickup deficit / IMPACT_FULL_LIFT)` | `dryrun.impact_score` counts only primary-KPI lift, so a flagged-caller-ID evacuation on an engagement-primary workflow scored 0.0 although it is the biggest lever. For a flagged evacuation the producer attaches `impact_override = sum over flagged DIDs of (traffic share moved off the DID in the largest allocation key) x (1 - q_est, the detector's estimated pickup ratio vs peers) / 0.10`, the same scale as every other impact (a 10% workflow-wide relative gain = 1.0). Example: 14.3% moved off a DID that picks up 69% worse = 0.099 / 0.10 = 0.99. Uses only numbers the DID detector already holds; the approver only checks impact is in [0,1] (sim/world.py), so approval outcomes are unchanged. | Linear in both factors; clipped to [0,1]. A supervisor-owned allocation uses the same formula on its minimal evacuation step. |

## Hallucination (C8)

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| ceiling `1 - min_validation_pass_rate` | policy | A fix needs validation pass >= `min_validation_pass_rate`, so a flag rate above `1 - pass` is, by the workflow's own governance, worse than anything approvable. Baseline-free test: Wilson lower bound (z=3.09) of the live prompt's rolling-day flag rate above it. | With a trusted baseline the ceiling is raised to `max(1 - min_pass, Wilson upper bound (z=3.09) of the known-good prompt's own flag rate)`: detector false positives (~1%) plus a low true rate exceed a strict 1% ceiling on a healthy prompt, so the absolute test is effectively cold-start only (the baseline comparison does the work afterwards). A prompt whose true rate sits under the ceiling (2.5% under a 3% ceiling) is not caught by this test; it needs a baseline or the Day-0 validation. |
| impact divisor | `1 - min_pass` | Impact override = flag-rate excess / the workflow's own tolerance (was a fixed 1%). | Strict policies (0.99) saturate impact sooner. |
| `HALLUC_P`, `HALLUC_P_DRIFT` | 1e-4, 1e-5 | CONTEXT p<0.001, tightened for repeated looks. Exact Fisher is used when either count < 20 or the baseline n < 1000 (z approximation unreliable). The old 10x-alpha adherence branch is removed. | - |
| `HALLUC_MIN_CONNECTS` | 200 | At a 1.5% baseline, 200 connects hold ~3 flags: the smallest sample where an exact test can reach 1e-4 against a 5% rate. | - |
| `HALLUC_FLAG_MARGIN_FRACTION` | 1/3 | Non-inferiority margin of the verify step = a third of the workflow's tolerance (1 - min_pass) = 1pp at 0.97. | Smaller = stricter verification and more n needed. |
| `HALLUC_VERIFY_MIN_CONNECTS` | 400 | At a 0.6% flag rate, n=400 gives se 0.4pp so the upper bound of the difference (1.645 se) is ~0.7pp, inside the 1pp margin. | n=200 cannot pass a true-equal prompt at a 1pp margin. |
| `HALLUC_VERIFY_MAX_CONNECTS` | 1500 | Between 400 and 1500 connects an unresolved non-inferiority check means wait, not fail (a clean prompt with a 1.7% observed rate cannot be shown within 1pp at n=413: upper bound 1.4pp; it can at ~1000). A fix is failed at once if significantly worse than baseline (p<0.01) or fails the engagement guardrail, and after 1500 connects if still not non-inferior. | Lower = quicker failing of ambiguous fixes. |
| `HALLUC_VALIDATION_N_STEPS` | 300,200,100,50 | Day-0 validation uses the incident credit rule and scales down only when credits cannot cover 300; 50 (1 credit) is the floor. | - |
| `HALLUC_RECHECK_FAILS` | 4 ticks | A production-triggered incident whose spike no longer holds on 4 consecutive evaluations (1 h) closes as a false alarm and the blacklist is lifted. | - |
| `HALLUC_BAD_EXPIRY_MINUTES` | 2 days | A blacklisted prompt is reconsidered after 2 days (evidence ages, supervisors fix prompts). | - |
| `INCIDENT_CREDIT_DAILY_CAP` | 30 per workflow per day | One incident may spend 25; the daily cap stops repeated false incidents draining credits. | - |

## Solo-DID own-history test (A1)

Used when a caller ID has no usable peer step test (a single active DID, or probes too thin to give peers 150
dials per window). The recent window is compared with the DID's own preceding 48 h at the (hour-of-day, cell)
level, times the change the fatigue curve predicts from its own load trajectory.

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `DID_SOLO_REF_HOURS` | 48 | The reference must contain every hour-of-day of the window, so it spans two days; a longer reference averages over fatigue drift. At 2,000 dials/day it holds ~4,000 dials (se_rel 3%). | 24 h can lack the window's hours of day; 96 h dilutes a slow decline. |
| `DID_SOLO_SHRINK_N` | 30 | An (hour, cell) rate from a few dials is shrunk toward the hour's pooled rate with 30 pseudo-dials: it removes lead-mix change without letting a sparse cell dominate. | 0 = noisy cell rates; 100 = hour-only adjustment. |
| `DID_SOLO_P_FACTOR` | 0.1 | Level = `DID_FLAG_P` x 0.1 (1e-6; 1e-8 while the curve is unfitted). No peer absorbs a common shock, so the bar is stricter; with the 12% effect-size gate and 2-eval persistence a 6 h window needs a ~25% drop at 1,200 dials. | 1.0 flags 12-25% steps but would flag on lead-mix drift. |
| `DID_SOLO_DAYS_BACK` | 4 | Cube days loaded: window + reference. | - |

## Sibling prompt safety check (A2)

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `SIBLING_MAX` | 3 | At most 3 other catalogue prompts per workflow, in catalogue order (summaries are never read: R5). | More siblings spend more of the 200 credits for the same single decision. |
| `SIBLING_N` | 200 | 2 credits per sibling. | At n=200 a 0.9% failure rate cannot be separated from a 2.7% one without a top-up (below). |
| `SIBLING_TOPUP_N` | 300 | One 3-credit top-up when the sibling's observed rate is below the live prompt's lower bound but its upper bound still overlaps. | Pooled n=500 lets the bounds separate a ~1 pp gap only about half the time. |
| `SIBLING_BOUND_Z` | 1.645 | One-sided 95% Wilson bounds on each side: sibling upper bound < live lower bound ("clearly safer"). | 1.96 needs roughly 40% more n. |
| `SIBLING_MIN_LIVE_FRACTION` | 0.5 | Materiality: the live prompt's failure lower bound must be at least half the workflow's tolerance (1 - min pass = 3%, so 1.5%). A first run switched a healthy prompt (true failure ~1%, 7/300 observed) to the strict-script prompt on bounds that merely separated: -14% engagement, graded harmful. With the gate a bound-separated but immaterial gap gets one 3-credit second look at the live prompt, then no switch. Note a switch away from a permissive prompt (e.g. 2.7% failure) still costs engagement by construction: it is a safety-vs-engagement trade the approver signs off. | 0.33 (the 1 pp non-inferiority margin) admits the false switch above. |
| credits | - | Routine spend rule: after every run the balance must still hold the incident reserve of every workflow. Reserve per workflow = `min(CREDIT_RESERVE_PER_WORKFLOW (25), credits_initial / (2 x W))`, so at most half the starting balance is held back (W=12, 300 credits: 12.5 each, 150 total, instead of an unreachable 300). The `credits_low` page uses the same reserve. | - |

Verification after apply reuses the C8 constants (`HALLUC_VERIFY_*`, flag margin = a third of the workflow's
tolerance, engagement guardrail). Engagement is not checked before apply (a catalogue prompt has no engagement
history): a switch can cost engagement relative to a permissive prompt, which is why a failed verification rolls back.

## Shared cohorts (C2)

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `COHORT_MIN_DIALS_PER_HOUR` | 100 | n_min = 100 x in-window hours (1,000 dials for a 10 h window). A cohort-hour pickup rate from 100 dials has se_rel 15% (see notation), the smallest at which the shrinkage estimate is not mostly prior. Groups below n_min fall into `default`. | 200: fewer, larger cohorts; 50: se_rel 21%, cohorts mostly shrunk to pooled. |
| `COHORT_MAX` | 20 | The sim's limit; the largest groups are kept. | - |
| `COHORT_MIN_Z` | 3.72 | The group x hour likelihood-ratio statistic is converted to a df-comparable z (Wilson-Hilferty) and must beat one-sided p<1e-4 = 1e-3 / 10 candidate partitions (4 features + 6 pairs). A BIC penalty was tried and rejected: it discards a real age effect (LR 114, df 27) on 27k dials. | 3.09 (p=1e-3) adds a false partition about 1 time in 100 null workflows. |
| `COHORT_PAIR_MARGIN_Z` | 2.0 | A feature pair must beat the best single feature by 2 z (parsimony: pairs add df and fragment volume). | - |

The score uses a separable (group + hour) multiplicative model as the null, so pickup LEVEL differences between
groups score zero: only differing hour PROFILES, which per-cohort tables can exploit, count. Cohorts are the groups of
one feature (or pair), so they are disjoint and first-match order cannot matter (`is_partition` checks it).

## Welcome x voice experiments (C6) and decay (C7)

Every value is in `controller/settings.py` (`EXP_*`) and none is read from a scenario. The rule itself lives in
`controller/exp_rules.py` and is applied unchanged by `scripts/mc_null.py` (results: `reports/mc_null.md`).

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `EXP_ENTRY_SHARE`, `EXP_MAX_CHALLENGER_TOTAL` | 7.5%, 22.5% | CONTEXT C6. A challenger that is 10% worse costs 0.75 pp of engagement at entry; three challengers cap the worst plausible entry step near 2% of expected engagement only if all are that bad. | Higher shares learn faster but make a bad entry step approach the 1% harmful line. |
| `EXP_RAMP_SHARE`, `EXP_MIN_CONTROL_SHARE` | 20%, 40% | CONTEXT C6. Control keeps at least 40% so the comparison and the harm-stop stay powered. | - |
| ramp / drop | 1 day, 100 connects; drop on the WHOLE-experiment z: <= -1.5 below 300 connects, <= -1 from 300 connects, otherwise defer; an arm already ramped to 20% is also dropped at last-24h z <= -1.5 (`EXP_RAMPED_DROP_RECENT_Z`) | CONTEXT C6. A drop costs only learning, and keeping a 7.5% entry arm for another day costs at most 0.075 x |effect|, so a noisy window must not drop it (the first version also dropped on any last-24h z <= -1). An arm already carrying 20% costs ~3x as much, so it keeps the recent-window decay check, at the stricter -1.5. The same predicates are re-run at apply time (below). The ramp needs only a non-negative point estimate. | z <= -0.5 drops noisy arms too early; MC: even with the whole-experiment rule about 60% of null arms are dropped at some daily look within 8 days; the cost is learning only. |

| `EXP_DESIGN_MDE`, power, `EXP_DESIGN_ALPHA` | 10%, 0.80, 0.05 | Information at which a 10% relative lift has 80% power at one-sided 0.05: I = (z_a + z_b)^2 / ln(1.1)^2 = 680 (information = 1/se^2 of the clustered log ratio). | Holm | family = every challenger ever entered in the dim | Step-down: rank r among the arms is tested at alpha/(m - r + 1). Counting dropped arms keeps it conservative. | - |
| alpha split | per workflow 0.05 = 2 dims x 0.025; per dim: workflow-level 0.02 + 2 groups x 0.0025 | Welcome and voice run concurrently, so the 0.05 is split across them (Bonferroni). A first version gave each dim the full 0.05: the Monte Carlo false-winner rate per experiment was 2.0%, but with 4 experiments per scenario null_01 drew one false promotion (rolled back a day later by CUSUM + holdout). The two pre-registered analysis groups (unions of the cohort partition, each >= 35% of traffic, cut near 50% of traffic by the natural order of the feature values) share the familywise level; a group deploys only if its own test passes. | A larger group share costs workflow-level power. |

| pickup guardrail | non-inferiority, z = 1.645, margin = the workflow's `pickup_rate_max_drop` | Per-lead clustered difference of pickup; the upper bound of the drop must lie under the margin. Needs about 1,500 dials per arm at pickup 0.3, so it can delay a promotion by about a day. | - |
| two-stage promotion | stage 1: winner 50% / old control 50% (`EXP_STAGE1_SHARE`); stage 2: winner 90% / holdout 10% (`EXP_HOLDOUT`) only after >= 24 h at stage 1 AND the recent-24h one-sided 95% lower bound > 0 AND the concurrent 50/50 contrast since stage 1 is positive | CONTEXT C7. The 10% holdout of stage 2 is about 90 connects/day. | Going straight to 90/10 halves the exposure to a decaying winner only if the decay test were as powered; it is not. |
| decay alarm (primary) | sequential winner-vs-control concurrent test: Mantel-Haenszel pooled clustered log-ratio since the monitoring epoch began, one-sided Lan-DeMets OBF boundary at `EXP_DECAY_ALPHA` = 0.10, a look each time the information has grown by 0.1; the epoch (information for 80% power at a -15% effect, about 170) ends and a fresh one starts when its information reaches 1 (a look at t >= 1 after a t = 1 look has no alpha left: +inf) | CONTEXT C7. Rollback is risk-reducing, so its level is looser than a promotion's: a false rollback loses a modest lift and one approval, a missed decay keeps a harmful variant live. Restarting epochs keeps the test sensitive to a decay that begins late (a single cumulative contrast would be diluted by the good days). | alpha 0.05: first-look bound ~3.7 -> ~4.3 sigma, roughly a day later. |
| CUSUM (secondary) | blocks of 150 connects, reference = the winner's own pre-promotion 48 h level (else first 3 blocks), k = 0.5, h = 3 | The winner's engagement is divided by the rate expected for its hour x cell mix (old control's pre-promotion cube history, shrunk with 20 pseudo-connects) so lead-mix swings do not alarm; each block is standardised by its binomial variance plus the reference's. | rollback routing | sequential alarm, OR CUSUM alarm AND holdout recent lift <= 0 | Risk-reducing: auto-apply where the workflow's policy allows the dim and the shift is within `max_shift` (stepped: each hourly step moves at most 0.95 x max_shift, so 50/50 -> control takes 3 steps at 0.2); otherwise the second-to-last approval slot (the last is reserved for safety incidents), severe priority, filed the first tick inside approver hours (superseding any routine request in flight). An approved stage-2 request that a rollback has superseded is never applied. | - |
| after the last look without a winner | a surviving challenger stays only while its point estimate >= control (the ramp criterion); otherwise it reverts to control in the next bundle, but only if the revert is not itself expected-harmful (expected engagement change on the observed arm rates, `EXP_REVERT_MAX_EXPECTED_DROP`) | The earlier "never revert" rule left arms at 20% with negative estimates for the rest of the run. A revert of an arm whose observed rate is below control is an expected gain by construction; the check exists so that a stale or noisy estimate can never justify a harmful revert. | - |
| apply-time veto | before `/apply` of an approved ramp, drop, or promotion stage: ramp - cumulative z above the drop bound and recent z above -1; drop - the drop predicate (cumulative, or recent for a ramped arm) still holds; promotion stage 1/2 - the recent-24h one-sided 80% lower bound (z = 0.84, `EXP_VETO_Z`) of the winner's lift > 0 | CONTEXT section 2: the grader judges each change at apply time, and approval takes 2-20 h. A bare point estimate passes about half of the arms whose true lift is zero; an 80% one-sided bound passes a zero-lift arm about 20% of the time. Withheld = `/apply` is never called (no lapse is logged), the decision is recorded, the experiment state is restored and re-plans at its next look; harm-stops and rollbacks are never withheld. | 95% (z 1.645): withholds more stable winners; 50%: the bare point estimate. |
| strata | Mantel-Haenszel weights n_a n_c / (n_a + n_c) per (day x config version) | Arm and control are compared within a share regime and a day, so ramps and calendar drift of the base rate cannot confound the contrast; the sandwich variance sums a lead's influence over strata. MC (reports/mc_null.md): at a +-5% drift stratified and unstratified contrasts false-promote at the same rate (1.3% each), so the pooling costs nothing and protects when shares and the base rate move together. | - |
| harm-stop (unchanged) | z <= -3 at >= 150 connects, 4-hourly | Over an 8-day run the repeated 4-hourly looks stop about 20% of NULL arms (a ~6-7 look/day random walk crosses -3 more often than the single-look 0.13% suggests). Accepted: a stop only removes a 7.5-20% arm (cost: lost learning on that arm), it never harms customers, and a truly bad arm (-10%) is stopped within ~1.5 days. | -3.5 halves the null-stop rate but delays a true -10% stop by ~2 days. |

Time effects: the pooled contrast is stratified by share regime x day (above), and the MC includes a +-5% calendar drift
of the base rate. Not modelled: lead-mix drift inside a day (arm assignment is per dial, so within a stratum it is balanced).

Decay detection has a physical bound: a decaying variant at 20% share carries ~180 connects/day, so a one-day contrast
has se ~10%; a lift falling from +15% to -10% over 2 days cannot be told from noise until about 3-4 days after onset
without a false-alarm rate that would drop healthy arms. `reports/mc_null.md` quantifies what each layer buys
(share of the decaying arm at onset + 2 days, exposure-days at the winner share, rollback latency in 4-hour ticks). Measured (`reports/mc_null.md`, 250 runs per row): a promoted decaying winner is rolled back in 24.0% of runs against 24.4% promoted in the first row (one run of 250 not rolled back within 16 days) and in every promoted run in the other four rows, a median of 11-14 ticks (~2 days) after stage 1 goes live, with ~1.1-1.2 exposure-days at the winner share after onset; the decaying arm's share is <= 0.1 at onset + 2 days in only 2-16% of runs (approval latency 20 h-2 h).

## Caller-ID weak-base rebalance (item 9)

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `DID_WEAK_PERSIST_DAYS` | 2 | A weak-base verdict (z <= -3.09 at comparable load, n >= 150) must hold on 2 distinct calendar days with no healthy evaluation in between. An earlier null_01 run produced a -2.2% DID-health rebalance from one false "weak" classification. | 3: a day slower on a truly weak DID. |
| `DID_REBALANCE_MIN_HEALTH_GAIN` | 0 | The rebalance (no flagged DID involved) must have a non-negative expected health change: sum over DIDs of share x observed pickup ratio at comparable load x fatigue-curve health at the load the DID would carry. ## Per-person call time (C4b, analysis only)

| Name | Value | Derivation | Sensitivity |
|---|---|---|---|
| `PERSON_PRIOR_STRENGTH` | 20 pseudo-dials per block | PRIOR, not measured. The cohort's block pickup is estimated from thousands of dials, so it is far more certain than any one person; 20 pseudo-dials means a person needs about 20 dials in a block to move the estimate half-way. With the 4-dial minimum the data weight is <= 17% (mean about 10% on public_01/02). The same weight shrinks sparse cohort blocks to the cohort average. | 5: person data counts 4x as much, more persons qualify, and so does the null (selection grows with it). |
| eligibility | >= 2 campaigns, >= 4 dials, >= 2 of 4 hour blocks | A returning person is the only one for whom a future call time can be chosen; one block gives no contrast between blocks. | - |
| `PERSON_PASS_PROB` | 0.8 | Would-assign only if P(best block pickup > cohort average) >= 0.8, exact Beta tail. The best block is chosen on the posterior mean, so this is a best-of-4 selection: `reports/person_analysis.md` shows the rule qualifies 75-90% as many persons when no person effect exists. | 0.95: far fewer qualifiers, nearer the null floor of zero. |
| decision | never a config change | `lead_preferred_hour` is x6 / x0.25 under fixed hourly capacity (CONTEXT section 3), and treated persons displace controls, so a person holdout is biased. The module imports no planner, governance or client code. | - |

## Filing window and approver budget (P4/P5)

| Setting | Value | Why | Sensitivity |
|---|---|---|---|
| `FILE_MIN_P_ROUTINE` | 0.9 | The sim decides at `next_working(now + U[lo,hi])` and expires the request if that is after `expires_at`. We compute P(decision <= expires_at) per filing minute (uniform latency, discretised per minute) and file a routine bundle only at P >= 0.9, so an expiry is rare and the next day's re-plan costs little. Public policies (ttl 24 h, or 12 h at latency <= 240) give P = 1.0 at opening, so their behaviour equals the old worst-case rule. | 1.0 reproduces the old rule and starves short-TTL policies; 0.5 expires about half of the routine bundles on those. |
| `FILE_MIN_P_URGENT` | 0.5 | Incident and severe requests are filed at a coin-flip chance of a decision before `expires_at` (raised from 0.3, which let a short-TTL incident request expire 70% of the time). An expired request is not free: it spends a fatigue slot for 24 h and counts as a hygiene failure, and the fix still waits. An incident is worth a 50% filing versus never filing (unmitigated harm and MTTR are graded); a routine bundle is not (it waits a day and re-plans), which is why routine stays at 0.9. | 0.3 expires most incident requests on short-TTL policies; 0.9 would never file an incident when the TTL is short. |
| `FILE_MIN_P_URGENT_FLOOR` | 0.10 | When no in-hours minute of the day reaches `FILE_MIN_P_URGENT` (short TTL against long latency, e.g. TTL 2 h: best P 0.43 on nw_renewal-like, 0.145 on nw_kyc-like policies), incident and severe requests are filed at the day's best minutes (P >= 95% of the best) if that best is at least 0.10 (`fatigue.urgent_need`). Never filing guarantees the safety fix never lands; a likely-expiring request costs one slot and one hygiene count. Below 0.10 nearly every request would expire, so nothing is filed. Routine stays at 0.9. | Untested end to end: unit tests only (`test_filing_probability.py`). |
| Budget of 1 per 24 h | routine and severe share the single slot | With total == 1 the old tiers gave routine 0 and severe 0, so only incidents could ever act. Trade-off, accepted on purpose: a routine bundle may consume the only slot, so an incident arriving right after a routine filing waits up to 24 h for it (a routine filing is one unit of tuning value every day; reserving the slot would mean it never runs). With total == 2 severe may use slot 1 and routine stays at 1; the last slot stays incident-only. | Reserving the slot for incidents means routine tuning never runs on such a workflow. |
| `FILE_MIN_P_ROUTINE_FLOOR` | 0.6 | When no in-hours minute reaches `FILE_MIN_P_ROUTINE` (short ttl against long latency, e.g. ttl 3 h on a 30-240 min approver: best P about 0.7), a routine bundle files at the day's best minutes (P >= 95% of the best) if that best is >= 0.6 (`fatigue.routine_need`); otherwise routine never files. A routine request that expires costs a fatigue slot and an 'expired' hygiene count; below 0.6 the expected waste exceeds the value of the bundle. Public policies have P = 1.0, so this is inert there. | 0.9 starves short-ttl policies of Day-0 cohorts/schedule/experiments; 0.3 expires most requests. |
| Apply-window factor | derived | `decision_probability` is multiplied by `min(tick, window_min + 1) / tick`: the sim decides at an integer minute D, the controller sees it at the next tick (delay 0..tick-1) and refuses to apply once `now > D + window`. Public: window 120 min >= tick 15, factor 1 (inert). Below `FILE_MIN_P_URGENT_FLOOR` the apply window is unreachable: nothing is filed and an `apply_window_unreachable` alert is written once a day. | - |
| `REFILE_AFTER_REJECT_MIN` | 120 | After the second rejection of one (workflow, kind) within 24 h, refiling waits `120 x (rejections - 1)` minutes (capped at a day), so an always-rejecting approver cannot burn the daily budget in consecutive ticks. The first rejection never delays the refile (public reject rates 5-15% behave as before); an EXPIRED request is unaffected. | Larger: slower recovery from a transient rejection streak; 0: every tick refiles. |
| `SOFT_CAPS_BY_TENANT` | `kestrel_finance` -> the ks_cancel cap | The soft cap applies to every workflow of the tenant (the sim exposes `tenant_id`); `SOFT_CAPS` stays as a per-workflow-id override. Same values, so the public scenarios are unchanged. | - |
| Soft caps (`SOFT_CAPS`) | honoured only if achievable | `not_before_hour` is applied only when it is before approver close and some filing minute at or after it still passes P >= 0.9; `max_per_day` only lowers the computed routine budget and is ignored below 1. An ignored cap writes a `soft_cap_ignored` decision row once a day. | - |
| `SUBMIT_FAILED_BACKOFF_MIN` | 240 sim minutes | A persistent 403/422 would otherwise resubmit a fresh id every tick, and each 403 on PUT is a graded `auto_apply_rejected`. | Shorter retries more often; longer reacts slower to a fixed policy. |
